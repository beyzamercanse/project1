Alytro

Release tests for the numbers your customers see.

Software teams test their code before every release. The dashboards, KPIs and reporting APIs they ship to customers usually don’t get the same care. A query can run without errors and still return the wrong retention rate, because the denominator changed or a join started duplicating rows. Nobody notices until a customer does.

Alytro is meant to catch that before the release goes out. A team writes down how its critical metrics are defined (grain, numerator, denominator, time window), pins a dataset and its reference results, and runs every release candidate against them. The result goes back to CI as pass, review or block, with the evidence attached. It works for hand-written SQL and for AI-generated analytics alike. It runs inside the customer’s own environment, so their data stays where it is.

It grew out of the same problem as my projects here. Most of the hard bugs I’ve dealt with weren’t crashes. They were numbers that looked plausible and were wrong.

How a release check works

  1. DefineAgree the metric contract: grain, numerator, denominator, window, exclusions.
  2. PinFix the dataset snapshot and the reference result, both hashed.
  3. CompareRun the candidate release and compare it with the reference and the previous release.
  4. DecidePass, review or block in CI, with the failing query and numbers attached.

Where it is

A working local prototype with 40 seeded test scenarios across retention, funnels, A/B tests and AI-written claims, plus a release comparison and a dashboard. Its test suite passes. It has not been benchmarked on real customer data yet, and I don’t treat the prototype’s results as accuracy figures.
