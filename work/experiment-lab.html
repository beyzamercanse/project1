Experiment Lab

A guided onboarding flow raised 7-day activation by 3.5 points. I recommended holding it anyway, because support contacts rose far past the limit agreed before the test. Then I went back and checked whether this test could have passed that limit at all.

Stack
Python (standard library), SQL (SQLite), GitHub Actions
Data
Simulated randomized test, 12,000 users, Sep–Oct 2026 (seed 418)
Code
beyzamercanse/experiment-lab

Goal

The product manager wanted to know whether to roll guided workspace setup out to every new user. The rule was written down before any data came in. Ship only if activation improves by at least 1.5 points and the upper bound of the support-contact increase stays at or below half a point. My job was the definitions, the estimate, and an answer the team could defend.

+3.52 pp7-day activation, 95% CI +1.90 to +5.15
+2.26 ppsupport contacts, 95% CI +1.49 to +3.03
p = 0.52sample-ratio check on 6,035 vs 5,965 users
Holdactivation passes, the guardrail fails

Architecture

  1. Raw files12,000 assignments, 27,796 events
  2. Validation4 events quarantined (unknown user or type)
  3. Deduplication437 replayed event IDs removed
  4. user_outcomesone row per assigned user, binary flags per window
  5. Summary + statsvariant counts, SRM, z-test, Wald intervals
  6. Decision rulethreshold + guardrail, fixed in advance
  7. Robustnessbootstrap and guardrail power, from the same database

One Python script and one SQL file produce the result. CI reruns everything from scratch and fails if any count, rate or conclusion differs from what is committed.

How it works

Denominator first

Every rate is divided by assigned users, not exposed users. About 4.5% never saw onboarding. Dropping them would turn a randomized comparison into a self-selected one, so they stay in (intent-to-treat).

Events become users

Events are deduplicated by ID before any join, then collapsed to one row per user with MAX(CASE …) flags. Three first_value events from one person still count once. A test pushes duplicates through the SQL and checks the user-level output.

Windows mean something

“7-day” is offsets 0–6 from assignment. D30 retention only counts users observed for 30 days. For younger cohorts it is null and shown as “not mature”, never as 0%, which would look like churn.

Checks before the call

A chi-square test for sample-ratio mismatch, a complete primary window for every user, and an audit that the raw events reconcile exactly: 27,796 = 27,355 accepted + 437 replays + 4 quarantined.

Second pass

After the first version I came back with two questions.

Is the normal approximation hiding anything?

I bootstrapped both differences by resampling users within each arm, 2,000 times with a fixed seed. The intervals barely move: activation +1.85 to +5.15 pp against +1.90 to +5.15 for Wald, support +1.51 to +3.01 against +1.49 to +3.03. With success counts in the hundreds that was expected, and the hold doesn’t depend on the method.

Could this test have passed the guardrail at all?

This turned out to be the more useful question. The rule asks the upper bound of the support increase to stay under +0.5 pp, which is a non-inferiority test, and those need large samples. With a 3.76% baseline and about 6,000 users per arm, a change with no effect on support would pass only 30% of the time. I didn’t want to trust the formula alone, so I simulated 1,000 harmless experiments through the same rule. That also came out at 30%.

Reaching 80% power at that margin would take about 22,730 users per arm. At the current size, the tightest margin you can reliably clear is about +1.0 pp. So the hold is right here, because the harm is large. But as designed, the guardrail would also have blocked most harmless changes. Before the next test I’d agree the sample size or the margin with the support team, in writing, before any data comes in.

Limits and next steps

The effects are built into the simulation, so this shows the method, not a real product result. Segments and retention are exploratory and I don’t draw subgroup conclusions from them. The data can show that support contacts went up but not which onboarding step caused it. The first thing I’d add before a rerun is step-level tracking and ticket reasons.
