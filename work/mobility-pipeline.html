Mobility Pipeline

The feed behind a daily trip report resends records, delivers trips days late and corrects fares afterwards. I built a batch pipeline that loads each delivery in a single transaction, quarantines bad rows, publishes only after reconciliation, and keeps a record of how much each day changed after it was first published.

Stack
Python (standard library), SQL (SQLite), GitHub Actions
Data
Generated taxi-style trips, 1–14 Jan 2026 (seed 4026). Not real TLC data.
Code
beyzamercanse/mobility-pipeline

Goal

An operations analyst needs daily trips, fares and pickup-zone demand every morning, and needs to know whether today’s snapshot can be trusted. With a naive append-only load, repeated deliveries inflate counts, late trips land on the wrong day and corrected fares change totals without warning. The goal is daily numbers that stay correct through all of that, with every input row accounted for.

Architecture

  1. Batch + manifestJSONL file, SHA-256, row count, schema version
  2. Verifychecksum, schema, row count; skip if already loaded
  3. Validate rowsbad rows to quarantine with reason and raw line
  4. tripslatest version per trip_id wins; same-version conflicts rejected
  5. Snapshotevery day’s trips and fare after this batch
  6. Martsdaily, zone, hourly, restatements, by event date
  7. Checkskeys, row accounting, values, mart totals, snapshot match
  8. Publishtemp file, then atomic replace

Facts, quarantine rows, the batch ledger entry and the snapshot for a batch commit together or not at all. A crash halfway through a batch leaves no trace, and the retry loads it cleanly.

How it works

Batches are immutable

A batch ID that was already loaded is skipped. The same ID with different bytes is an error, not an overwrite. Rerunning the whole pipeline reports skipped_unchanged three times and writes a byte-identical dashboard file, which CI checks.

One bad row doesn’t block the rest

Missing fields, non-canonical timestamps, impossible durations, unknown zones and out-of-range fares go to quarantine with a reason code. The other 7,000 rows still load, and the reject count sits on the dashboard next to the metrics.

Versions decide, not arrival order

Trips are keyed by trip_id and ordered by updated_at. Newer replaces older, and older or identical counts as a duplicate. Loading the three batches in reverse order gives the same final trips and fares. A test checks that.

Days are event days

Marts group by pickup date, so a trip that arrives two days late is counted on the day it happened. The daily figures stay correct, but it also means a published day can change. That’s what the restatement audit is for.

Restatement audit

Grouping by event date fixes history, but people notice when yesterday’s number is different today. I wanted those changes to be visible and measured, not something two reports disagree about.

After each batch commits, and inside the same transaction, the pipeline stores every day’s trip count and fare in integer cents. A SQL view then compares each day’s first published value with its current one, counts the later batches that changed it, and records which batch made the last change.

In this data every day moved twice. The late-arrival batch added 379 trips (+$9,205.00) to days that had already been published, and the correction batch changed fares by +$255.00 without adding trips. Each day ended up about 27 trips and 4.8–7.5% of fare higher than first reported. The largest change was 1 January, +$848.49. With a p95 arrival lag of 50 hours, I’d mark a day as provisional for its first two days and final after that. Now there’s a table to back that rule up.

Limits and next steps

This is single-writer, local and small, with no claims about production throughput. Real NYC TLC data comes as monthly Parquet without a trip ID, update timestamp or arrival time, so the versioning logic doesn’t carry over directly. The next step is a Parquet adapter with its own lineage (source file and row number), a contract for that source, and a measured runtime for one full month.
